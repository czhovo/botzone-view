# 四个 GitHub 来源可用性核验

核验日期：2026-10-16。目标：判断是否能作为当前黑白棋框架的参考 bot。已下载实际源码、核对外部数据、使用项目的 MinGW C++ 编译器编译和进行局部运行检查；尚未进行完整对局或强度测量。

| 来源 | 结论 | 实际缺口 |
| --- | --- | --- |
| [Wugengxian/---ai](https://github.com/Wugengxian/---ai) | 源码和评估数据齐全，Python 原程序可运行；当前框架不能直接使用 | 需要 C++ 移植及计时适配，不缺权重 |
| [alxdsptr/reversi](https://github.com/alxdsptr/reversi) | 公开版本是未完成的搜索框架，不能作为完整原版参考 bot | 多个评估函数及核心评估值计算未实现 |
| [programmingLearner/Reversi](https://github.com/programmingLearner/Reversi) | 完整 C++ 游戏与 AI 核心可用，可以继续接入 | 需要比赛协议适配和限时处理，无外部模型依赖 |
| [Walleclipse/Ultimate_Reversi](https://github.com/Walleclipse/Ultimate_Reversi) | C++ AI 核心可提取，但存在已复现错误，修复后才能验证为可靠参考 bot | GUI 剥离、比赛协议、时间限制及终局计分错误 |

## Wugengxian/---ai

`game.py` 依赖 NumPy 和仓库内 `data/data.json`。数据文件为 4,160,410 字节，是真实 JSON，不是 Git LFS 指针。11 组数值表均完整且为有限数值：13 个阶段，每阶段的 diag4/5/6/7/8 分别为 81/243/729/2187/6561 项，lc1–4、corn 各 6561 项，parity 为 2 项；另有 297 条开局库记录。

未修改原程序，用 Botzone 初始 JSON 请求运行，退出码 0，输出 `{ "response": { "x": 4, "y": 5 } }`。本次耗时约 7.328 秒，包含 Python/NumPy 启动与原本设定的 6 秒搜索，超过当前 2.5 秒动作限制。当前项目要求游戏程序使用 C++，因此需要移植才能进入正式参考对战流程，不能据此声称缺数据。

源码还存在可定位的问题：JSON 开局库的键为字符串，而查找时使用整数，因此不会命中；`stage >= 54` 写在 `stage >= 50` 的 elif 后面，不可达。这些是公开版本代码问题，不是缺少权重。未修正原文件。

移植复核更正：本报告先前把 `get_move(cur, opp)` 误认为重复查询当前方。实际函数参数顺序是 `(opp, cur)`，此处查询的是对手，因此原跳步判断正确。

## alxdsptr/reversi

原版 `main.cpp` 编译退出码 0，初始简化 Botzone 文本输入 `1\n-1 -1\n` 能输出落子，不能将此等同于完整可用。

`board.h` 中 `potential_mobility`、`stable_cnt`、`compute_corner` 均为空函数，明确写着 `finish it yourself`。`compute_score` 直接使用未初始化的 `cor`、`mobility`、`potential_mob`、`stability`、`pos`。编译器对无返回值和未初始化变量均给出诊断。自行补齐会构成新的评估器，不能冒充作者完整版本或沿用其 README 的约 1900 分自述。另有跨线程普通 bool 计时标志、无着法路径 ans 未赋值等问题。

## programmingLearner/Reversi

用户给出的个人主页置顶了实际仓库 Reversi。源码为旧 GB2312/GBK 编码，仓库 Makefile 本身也通过 iconv 转 UTF-8；核验中保留原字节，仅将检查副本转 UTF-8。全部 12 个 C++ 源文件整体编译通过。

独立检查程序调用原版 `AI.cpp`、`reverse.cpp`、`judge_end.cpp`，使用原默认搜索深度 8、残局搜索阈值 48、关闭调试输出，返回合法初始落子 `(2,3)`，耗时约 1.328 秒。评估参数全在源码，不读取模型文件。它现在是菜单式终端游戏，不是 Botzone/arena 程序；还需接入输入输出协议、处理 pass，并加入或约束计时。单次开局检查不能证明全盘都满足 2.5 秒限制。

## Walleclipse/Ultimate_Reversi

原工程要求 Visual Studio 2017 + EasyX，附有桌面 exe、图片和音乐。源码中 `document.dat` 用于保存/读取棋局，不是 AI 权重。困难 AI 的估值权重、搜索与置换表都在 `source.cpp`。

检查中按原源码范围提取棋盘操作和困难 AI，去掉 GUI/网络声明，仅对未使用的绘图函数提供无绘制实现；搜索与评估函数保持原样。提取的 C++ 核心编译退出码 0，调用 `Difficult()` 返回 `(5,4)`，原版 `Judge` 确认合法，本次进程耗时约 3.343 秒。原每步搜索设为 3000 ms，不适合直接放入当前 2.5 秒限制。

已实际复现错误：`getGameEndEval` 中 myscore 与 oppscore 两个分支都判断 `board[i][j] == myplayer`，导致 oppscore 永远不增长。将棋盘设为全白、myplayer 设为黑，返回 0，正确结果应判黑方失败；函数也忽略传入 color 的使用。因此只能认定核心可提取，不能认定原版已通过完整规则与稳定性验收。

## 证据与边界

- `sources.json`：四份来源 URL、提交哈希、文件大小与 SHA-256。
- `check-results.json`：首次全部编译/运行命令、退出码、时间、原始诊断。首次 programming 核心探针少链接一个原仓库函数，随后已补齐并通过，见后续结果。
- `additional-check-results.json`：修正检查程序后的编译/落子结果，以及 Wugengxian 全部数据表形状校验。
- `checks/`、`inspection/`：可复查的探针和编码转换副本。四个原始仓库文件均未编辑。
- 本次只检查可用性，未修改既有参考 bot 选择、448 局记录或页面。四份新来源均无本次实测 Elo；不能用仓库描述推断强度。
